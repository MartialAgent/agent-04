## 1. 왜 4개 축인가

🟢 **전원**

에이전트 "개발 방식"은 **하나의 스펙트럼이 아니라 서로 독립적인 4개 축의 조합**으로 봐야 정확합니다. `[판단]`

흔한 오해는 이렇게 한 줄로 세우는 것입니다.

```
❌  ChatGPT  <  Dify  <  LangGraph  <  Claude Code
    (쉬움)                            (어려움·좋음)
```

**이렇게 세울 수 없습니다.** 흐름을 코드로 짜면서(A3) 데이터를 클라우드로 보낼 수도 있고(B1),
노코드로 만들면서(A2) 자체 서버에 두뇌를 둘 수도 있습니다(B3). **네 축이 따로 돕니다.**

| 축 | 묻는 것 | 값 |
|---|---|---|
| **A. 오케스트레이션** | 흐름을 누가/어떻게 정하나 | A1 → A4 |
| **B. 모델 호스팅** | 두뇌를 어디에 두나 | B1 → B3 |
| **C. 지식 주입** | 사내 규정·문서를 어떻게 태우나 | C1 → C4 |
| **D. 근거·검증** | 틀린 말/근거 없는 말을 어떻게 막나 | D1 → D2 |

그래서 어떤 방식이든 **네 글자로 적을 수 있습니다** — 예: `A3 + B1 + C2 + D1`.

## 2. 축 A — 오케스트레이션 (흐름을 누가 정하나)

🟢 **전원**

| 유형 | 대표 도구 | 흐름 결정 주체 | 성격 |
|---|---|---|---|
| **A1. 순수 프롬프트 / 시트 함수** | ChatGPT 대화, Excel·Sheets AI 함수, Copilot | 사람이 매번 지시 | 에이전트라기보다 **"AI 보조"**. 상태·분기 없음 |
| **A2. 노코드/로우코드 플랫폼** | **Dify**, n8n, Flowise, Coze, Make | GUI로 그린 노드 그래프 | 분기·지식베이스·챗봇을 드래그로 조립. **비개발자 접근성↑** |
| **A3. 코드 프레임워크 오케스트레이션** | **LangGraph**, CrewAI, AutoGen | 개발자가 상태그래프를 코드로 명시 | 흐름이 **결정적·재현가능**. IP 자산화·정형 반복에 강함 |
| **A4. 모델주도 하네스(agentic harness)** | **Claude Code**, Cursor Agent, OpenAI Agents SDK | 모델이 도구를 골라 스스로 진행 | **유연·비정형** 과제에 강함. 흐름은 모델 판단에 의존 |

`[일반원칙]` A1 → A4로 갈수록 **자율성·유연성은 오르고, 흐름의 예측가능성·감사추적성은 설계에 더 신경 써야 합니다.**

> 💡 **04기가 지금 서 있는 자리**
> 2-2단계와 4-1단계에서 만든 건 전부 **A3**입니다. 그리고 여러분이 지금 이 리포를
> 클로드에게 시켜 고치고 있다면 그건 **A4**를 쓰고 있는 것입니다.
> **둘을 이미 다 써봤습니다.** 이름을 몰랐을 뿐입니다.

## 3. 축 B — 모델 호스팅 (두뇌를 어디에 두나)

🟢 **전원** · **비개발자에게 가장 중요한 축입니다.** 기술이 아니라 **데이터 반출** 문제이기 때문입니다.

| 유형 | 예 | 데이터 경계 |
|---|---|---|
| **B1. 클라우드 상용 API** | OpenAI GPT, Anthropic Claude(API), **Gemini API** | 프롬프트·문서가 **외부 사업자로 전송됨** |
| **B2. 로컬 실행 + 클라우드 모델(하이브리드)** | 색인·검색·OCR은 로컬, 추론만 클라우드 | 원문은 로컬, **발췌·질의는 외부로 나갈 수 있음** |
| **B3. 자체호스팅 오픈웨이트** | 사내 GPU + Qwen/Llama 등 온프레미스 | 데이터가 **사내망을 벗어나지 않음**(에어갭 가능) |

> ⚠️ **이 리포의 모든 실습은 B1입니다.** `.env`의 `GOOGLE_API_KEY`로 구글에 보냅니다.
> **학습용이라 괜찮지만, 회사 실데이터로는 그대로 하면 안 됩니다.**
> 각자 조직의 반출 규정을 먼저 확인하세요. 그게 B축 선택입니다.

## 4. 축 C — 지식 주입 (사내 문서를 어떻게 태우나)

🟢 **전원**

| 유형 | 방식 | 비고 |
|---|---|---|
| **C1. 프롬프트 첨부** | 문서를 대화창에 붙여넣기 | 소량·일회성. **확장성 없음** |
| **C2. 플랫폼 내장 지식베이스** | Dify Knowledge, GPTs 파일 | RAG를 GUI로. **색인 세부 제어는 제한적** |
| **C3. 자체 하이브리드 RAG** | 벡터 + BM25 + RRF + 메타 필터 | 색인·마스킹·인용을 **직접 통제** |
| **C4. 파인튜닝** | 가중치에 지식 각인 | **PII 각인 위험**·갱신 비용 큼 |

> 2-2단계의 `INVENTORY` 딕셔너리는 **C1의 가장 원시적인 형태**입니다.
> 데이터가 코드 안에 박혀 있죠. 실무로 가면 C2 이상이 필요해집니다.

> ⚠️ **C4는 대개 답이 아닙니다.** 개인정보가 가중치에 각인되면 지울 수 없고,
> 내용이 바뀔 때마다 다시 학습해야 합니다. **먼저 C3(RAG 런타임 조회)를 검토하세요.**

## 5. 축 D — 근거·검증·거버넌스

🟢 **전원** · **"AI가 지어내면 어떡하냐"에 대한 구조적 답입니다.**

| 유형 | 방식 |
|---|---|
| **D1. 모델 신뢰 (프롬프트 의존)** | "출처를 달아줘"라고 **부탁만 함** |
| **D2. 스키마 강제 + 기계검증 + 사람승인(HITL)** | 근거 없는 주장은 **생성 자체를 차단**, doc_id 실재를 **코드로 검증**, 확정은 **반드시 사람** |

D2가 실제로 어떻게 구현되는지가 중요합니다. 원문 사례의 **3중 계층**입니다. `[사실]`

| 계층 | 무엇을 | 어떻게 |
|---|---|---|
| **1. 생성 차단** | 근거 없는 주장을 **애초에 못 만들게** | 스키마가 각 주장에 `evidence`(문서 ID) 최소 1개를 강제(`min_length=1`). 모든 주장은 `verified="pending"`으로 태어남 |
| **2. 기계검증** | 그 문서 ID가 **실재하는지** | 검증 스크립트가 색인을 조회해 주장별 PASS/FAIL을 **결정적으로** 판정 |
| **3. 사람승인** | 최종 확정 | `approve()`가 ① 사람 승인자 ② 전 주장 `verified=="passed"` **둘 다 없으면 예외** |

> 🎯 **1번이 핵심입니다.** "지어내지 마"라고 부탁하는 게 아니라,
> **근거 필드가 비면 객체가 만들어지지 않게** 만든 것입니다.
> 프롬프트가 아니라 **타입 시스템으로 막은 것**입니다.

거버넌스로 함께 가는 것들: PII 마스킹을 **모델에 도달하기 전 색인 단계**에서 수행 ·
전 호출 감사로그(JSONL) · 응답마다 출처 인용 강제 · 인젝션 방어 래핑 · 미색인 파일 로깅. `[사실]`

## 6. 축 A 심화 — 하네스 vs 프레임워크

🔴 **개발 트랙** · A3(LangGraph)와 A4(Claude Code) 중 무엇을 고를지의 문제입니다.

### 6-1. 먼저 층위를 정리한다

가장 흔한 오해: *"MCP가 LangGraph를 쓴다"* / *"LangGraph가 MCP를 대체한다"*.
**셋은 경쟁 관계가 아니라 역할이 다른 부품입니다.** `[일반원칙]`

| 요소 | 정체 | 역할 | 비유 |
|---|---|---|---|
| **MCP** | 프로토콜(표준) | 툴·데이터를 모델에 연결하는 **규격** | USB-C |
| **LangGraph** | 오케스트레이션 프레임워크 | 흐름(노드·엣지·상태)을 **설계**하는 코드 뼈대 | 회로 기판 |
| **Claude / Gemini** | 모델(LLM) | 실제 **판단·생성**하는 두뇌 | CPU |

- MCP는 실행 주체가 아니라 **중립 연결 규격**입니다. LangGraph도, Claude Code도 MCP를 *경유해서* 툴을 가져옵니다
- 올바른 방향: **"LangGraph가 MCP를 통해 툴을 붙이고, 노드에서 모델을 두뇌로 호출한다."**

### 6-2. 두 조립 방식

**(A) LangGraph 중심 — 흐름을 직접 설계**

```
[LangGraph 그래프(흐름 설계)]
   ├─ 노드에서 모델 호출 (판단)
   └─ langchain-mcp-adapters 로 MCP 서버 붙임 (툴)
```

**(B) Claude Code 중심 — LangGraph 없음, 하네스가 흐름 내장**

```
[Claude Code 하네스(흐름 내장)]
   ├─ Claude가 직접 흐름 판단 (model-driven)
   └─ .mcp.json 으로 MCP 서버 붙임 (툴)
```

- 두 방식 모두 **MCP는 그대로 붙습니다.** 갈리는 것은 **"흐름을 누가 잡느냐"** 뿐입니다 `[판단]`
- **(C) 하이브리드**: 바깥 뼈대는 LangGraph(결정론), 특정 노드만 Claude Code/Agent SDK 자율 루프에 위임. **실무 절충안** `[판단]`

### 6-3. 핵심 트레이드오프 — 자율성 vs 결정론

| 항목 | Claude Code (하네스) | LangGraph (프레임워크) |
|---|---|---|
| 에이전트 루프 | 하네스 내장(기성품) | **직접 구현** |
| 제어 흐름 | 모델이 판단(자율적) | 노드/엣지로 명시(**결정론적**) |
| 상태 관리 | 하네스가 컨텍스트로 처리 | 명시적 `State` + 체크포인터 |
| MCP 연결 | config 등록만 | 코드에서 로드 |
| Human-in-the-loop | 권한 프롬프트 | `interrupt` 노드 직접 설계 |
| 재현성·감사성 | 실행 로그 위주 | **그래프 정의 = 명세**, step별 상태 저장 |
| 구축 비용 | **거의 0**(즉시 사용) | 그래프 설계·코딩 필요 |
| 모델·툴 이식성 | Claude에 고정 | **모델 교체 자유**(GPT/Gemini/로컬) |

> **"다른 API 활용 확장성"에 대한 정정**: 외부 API 연동 **자체는 Claude Code도 MCP·Bash·서브에이전트로 가능**합니다.
> LangGraph만의 확장성은 "외부 API를 쓸 수 있느냐"가 아니라
> **① 흐름을 모는 두뇌 모델을 비-Claude로 교체 가능 ② 코드에서 직접(in-code) 호출**이라는 두 지점입니다. `[판단]`

### 6-4. 목적별 선택

| 목적 | 추천 | 이유 |
|---|---|---|
| 내부 실무 자동화 | **Claude Code** (정형업무만 하이브리드) | 셋업 0·즉시 자율 |
| 실무자 교육 상품 | **Claude Code** | 저단가·대중·낮은 진입장벽 |
| 개발자 심화 교육 상품 | **LangGraph** | 고단가·개념 재료 풍부 |
| 고객 납품 솔루션 | **LangGraph** | IP 자산화·커스터마이즈·벤더 독립 |

**분기점은 두 가지입니다.** `[판단]`

1. **흐름의 결정론·감사성이 규정으로 요구되는가**
2. **결과물을 코드 자산으로 소유·재판매해야 하는가**

- **일회성·유동적 작업**(자료조사, 초안) → Claude Code 우위(즉시·자율)
- **반복·정형 워크플로**(승인 단계·증빙 체크 고정) → LangGraph 우위(재현·안정). 초기비 크나 정상상태 단가 낮음
- **하이브리드가 현실적 최적** — 규정된 프로세스는 LangGraph 결정론으로, 탐색·초안 생성은 Claude Code 자율 루프로 `[판단]`

## 7. 사례 — 두 조직을 4축에 놓아보기

🟡 · **분류를 배우는 가장 빠른 길은 실제 사례를 찍어보는 것입니다.**

원문이 대조한 두 사례입니다. 둘 다 "내부감사 업무에 AI 에이전트를 붙인다"는 **같은 목표**인데,
**네 축이 전부 다릅니다.**

### 사례 A — 사내 감사 보고서 에이전트 (실제 구축)

한 줄 요약: **A4 + B2(지향 B3) + C3 + D2** `[사실]`

- **A4** — LangGraph 같은 별도 오케스트레이터를 **의도적으로 두지 않고** Claude Code 자체를 런타임으로 사용. 사람 승인은 "대화 안에서 승인"으로 구현. 단, 정형 반복 워크플로에 한해 LangGraph `draft→critic` + `interrupt()` 게이트를 확장으로 남겨둠 → **현재 A4, 장기 A3 하이브리드 지향**
- **B2→B3** — 색인·검색·OCR·임베딩은 전부 로컬, 추론 두뇌만 클라우드. 실데이터용으로는 **자체호스팅(B3)을 권고**하되 현 구현체는 B2
- **C3** — 벡터(코사인) + BM25 → **RRF 융합(k=60)** + 메타데이터 사전필터. 임베딩 교체형. **파인튜닝은 금지**(PII 각인 방지)
- **D2** — 5절의 3중 계층 그대로
- **도구 관리** — 로컬 MCP 서버, 도구는 **읽기전용 2종만**. 도구 추가는 의사결정 기록 없이 금지("도구 과잉" 경계)

### 사례 B — 1일 핸즈온 교육 커리큘럼

한 줄 요약: **A1+A2 + B1 + C2 + D1** `[사실]`

- **A1→A2** — 오전은 LLM 기초·구조화 프롬프트·스프레드시트 AI 함수(A1), 오후는 **Dify** 노드 연결·분기로 챗봇 조립(A2)
- **B1** — 사전준비가 **유료 구독 + 개인 명의 신용카드 + API 크레딧 충전 + API 키**. 즉 클라우드 상용 API 전제
- **C2** — Dify 지식베이스 연동으로 내부 규정 Q&A. 색인·마스킹 세부 제어는 플랫폼에 위임 `[추정]`
- **D1** — 구조화 프롬프트(JSON/XML 태그)로 **출력 형식은 잡지만**, 근거 강제·기계검증·승인 게이트는 없음 `[판단]`

### 정면 비교

| 축 | 사례 A (구축) | 사례 B (교육) |
|---|---|---|
| **A. 오케스트레이션** | A4 모델주도 하네스, 장기 A3 지향 | A1 프롬프트 → A2 노코드 |
| **B. 모델 호스팅** | B2 로컬+클라우드, **B3 권고** | **B1 클라우드 상용 API** |
| **C. 지식주입** | C3 자체 하이브리드 RAG | C2 플랫폼 내장 KB |
| **D. 근거·검증** | **D2 스키마+기계검증+HITL** | D1 구조화 프롬프트 |
| 데이터 경계 | 원문 로컬, PII 색인단계 마스킹 | 프롬프트·문서가 외부로 전송 |
| 개발 주체 | 개발자(파이썬·MCP·색인) | **비개발자 친화**(GUI·노코드) |
| 결과물 성격 | 재현가능·감사추적 가능한 파이프라인 | **빠른 동작 프로토타입** |
| 비용 구조 | 구축 투자(초기↑, 데이터 통제) | 구독+종량제(진입↓, 유출 리스크) |
| 확정 권한 | **항상 사람**(코드로 강제) | 사람이 검토(강제 장치 없음) |

### 해석 — 왜 갈렸고 무엇을 취할까 `[판단]`

- **두 방식은 대립이 아니라 성숙도 단계가 다릅니다.** B는 "빠르게 붙여보는 입문·프로토타이핑"에, A는 "근거·재현·데이터통제가 1급 요구인 프로덕션"에 최적화됐습니다
- **결정적 차이는 축 B와 D입니다**
  - **B** — 실데이터(개인정보·미공시 재무·제보)를 클라우드 상용 API로 보내는 순간 반출 이슈가 생깁니다. 커리큘럼이 **"법인카드 불가, 개인 신용카드"** 를 요구하는 것 자체가 이 방식이 **개인 학습용이지 사내 실데이터 운영용이 아님**을 시사합니다
  - **D** — 보고서는 "근거 없는 문장"이 곧 리스크입니다. D1(프롬프트 의존)으로는 환각·무근거 주장을 **구조적으로 막지 못합니다**
- **권고 조합**: 교육에서 **개념·프롬프트 설계·노코드 프로토타이핑 감각**을 익히고 → 실데이터 단계에서 **로컬 RAG + 근거강제·검증 파이프라인 + 자체호스팅**으로 이관. 노코드(A2)는 **흐름 시각화·비개발자 협업**에, 코드/하네스(A3·A4) + 자체 RAG(C3)는 **근거·통제**에 각각 상보적입니다

> 🎯 **04기에게 이 사례가 주는 것**
> 배경이 다른 원우가 **같은 팀에서 일할 때 어디서 갈리는지**가 이 표에 있습니다.
> 비개발자가 A2로 프로토타입을 만들고, 개발자가 A3로 옮기는 것 — **그게 협업의 정상 경로입니다.**

## 9. 내 도메인을 4축에 놓기

🟡 · **이 절이 이 문서의 목적입니다.**

### 9-1. 지금 내 자리 찍기

| 축 | 지금 내가 하는 것 | 근거 |
|---|---|---|
| **A** 오케스트레이션 | A ___ | |
| **B** 모델 호스팅 | B ___ | |
| **C** 지식 주입 | C ___ | |
| **D** 근거·검증 | D ___ | |

> 이 리포 실습의 기본값은 **A3 + B1 + C1 + D1**입니다.
> ([2-2단계 `agent.py`](../02-web/02-web-goal/agent.py) = LangGraph + Gemini API + 코드 내 딕셔너리 + 검증 없음)

### 9-2. 실데이터로 갈 때 어디가 먼저 깨지나

**한 축씩 올립니다. 네 축을 동시에 올리려 하면 아무것도 안 끝납니다.**

| 질문 | 예 → 올려야 할 축 |
|---|---|
| 우리 조직 문서를 넣어야 하나? | **C1 → C2/C3** |
| 그 문서에 개인정보·미공시 정보가 있나? | **B1 → B2/B3** (+ 색인단계 마스킹) |
| 결과물이 틀리면 누가 책임지나? | **D1 → D2** |
| 비개발자가 흐름을 직접 고쳐야 하나? | **A3 → A2** (내려가는 것도 선택입니다) |
| 매번 다른 판단이 필요한 비정형 업무인가? | **A3 → A4** |

> 🎯 **네 번째 줄을 특히 보세요.**
> **축을 내리는 것도 정답일 수 있습니다.** 노코드가 코드보다 나쁜 게 아니라,
> **비개발자가 직접 고칠 수 있다는 것이 그 조직에서는 더 중요한 요구**일 수 있습니다.

### 9-3. 우선순위 판단 🟢

내 도메인에서 **가장 먼저 올려야 할 축 하나**를 고르고, **왜 그것인지 한 줄**로 적으세요.

```
내가 먼저 올릴 축: ______
이유:
```

> 대부분의 조직에서 답은 **B 아니면 D**입니다.
> A와 C는 "더 좋게" 만드는 축이지만, **B와 D는 "사고를 막는" 축**이기 때문입니다.
