# PRD — 에이전트 껍데기 (Agent Shell)

> **PRD = Product Requirements Document.** "무엇을, 왜, 누구를 위해"를 적는 문서입니다.
> 코드 이야기는 없습니다.

---

## 1. 한 줄 요약

**2-1단계의 채팅창 뒤에 "판단하고 도구를 쓰는 에이전트"를 넣고, 그 과정을 화면에 보이게 한다.**

---

## 2. 왜 만드나

2-1단계 마지막에 이 아쉬움이 남았습니다.

> "규칙표에 없는 말을 못 알아듣는다."

규칙을 100개로 늘려도 101번째 질문에서 똑같이 막힙니다. 규칙을 더 쓰는 건 답이 아닙니다.
필요한 건 **판단하는 것**입니다.

그런데 판단만으로도 부족합니다. 모델은 **우리 회사 재고도, 우리 부서 규정도, 내 연구실 서지 목록도 모릅니다.**

| | 챗봇 | **에이전트** |
|---|---|---|
| 동작 | 질문 → 답 (1회성) | **판단 → 행동 → 확인 → 다시 판단** (반복) |
| 도구 | 없음. 아는 것만 말함 | **도구를 직접 씀** (조회·계산·검색) |
| 모르는 걸 물으면 | 그럴듯하게 **지어냄** | 도구로 **찾아본 뒤** 답함 |
| 비유 | 안내데스크 직원 | 일을 통째로 맡기는 비서 |

**도메인 적용에서 이 차이가 결정적입니다.**
"재고 있어요?"에 챗봇은 그럴듯한 숫자를 지어냅니다. 에이전트는 재고표를 **찾아보고** 답합니다.

---

## 3. 누가 쓰나

| 사용자 | 원하는 것 |
|---|---|
| 우리 팀 동료 | 물어보면 **우리 데이터에 근거한** 답이 오는 것 |
| 나 (만드는 사람) | 에이전트가 **뭘 보고 그렇게 답했는지** 확인되는 것 |
| 관리자 | 사람마다 대화가 **섞이지 않는** 것 |

---

## 4. 무엇이 되면 성공인가

- [ ] 채팅창에 품번을 물으면 **더미 재고표를 조회해서** 답한다
- [ ] 답변 아래에 **에이전트가 밟은 단계**(판단 → 도구 실행 → 판단)가 보인다
- [ ] 답변 아래에 **어느 데이터를 봤는지** 근거가 표시된다
- [ ] 도구가 **필요 없는 질문**(인사 등)에는 도구를 쓰지 않고 바로 답한다 ← ★
- [ ] 이름을 넣고 들어가면 **사람마다 대화방이 나뉜다**
- [ ] 새로고침해도 **내 대화방의 대화가 남아 있다**
- [ ] 만드는 사람이 **노드 / 엣지 / 상태 / 조건분기 / 반복**을 코드에서 짚을 수 있다

마지막 줄이 진짜 목표입니다.

> ⚠️ 네 번째 항목이 특히 중요합니다.
> **도구를 항상 쓰면 그건 에이전트가 아니라 그냥 파이프라인입니다.**
> **쓸지 말지 판단하는 것**이 에이전트입니다.

---

## 5. 더미로 처리하는 것 (그리고 그 이유)

| 진짜 대신 더미로 | 진짜라면 | 왜 더미인가 |
|---|---|---|
| **LLM 판단** → `brain.py`의 규칙 | Gemini / GPT 호출 | 키 발급·과금·네트워크 오류에서 전원이 시간을 다 씀. **진짜 모델은 3~5단계** |
| **사내 데이터** → `data.py` 딕셔너리 | ERP API, Supabase | DB 붙이는 건 2-2의 주제가 아님 |
| **로그인** → 이름만 적으면 통과 | Google OAuth, Supabase Auth | 인증 구현에 하루가 감. **"자리"만 만들어두면 충분** |
| **배포** → `localhost` | AWS, Render | 계정·카드 등록에서 시간을 다 씀 |

> **그래도 배울 건 다 배웁니다.**
> 그래프 구조, 도구 호출, API 계약, 토큰이 오가는 방식 — 전부 진짜 그대로입니다.
> 나중에 진짜로 바꿀 때 **갈아끼우는 파일이 어디인지도 정확히 알게 됩니다.**

---

## 6. 일부러 **안 하는** 것

| 안 하는 것 | 이유 |
|---|---|
| 진짜 LLM 호출 | 3~5단계 |
| 진짜 인증 (비밀번호·OAuth) | 더미로 자리만 |
| 데이터베이스 | 서버 메모리. DB가 왜 필요한지는 짚고 넘어감 |
| React 등 프레임워크 | 2-1과 같은 이유 |
| 스트리밍 (답이 한 글자씩 나오는 것) | 구조가 복잡해짐. 목표 밖 |
| 멀티 에이전트 | 4단계 소재 |
| 배포 | 개념 설명 + Agent Room 실물 시연으로 대체 |

---

## 7. 만드는 순서와 그 이유

**프론트 한 번, 백 한 번씩 번갈아** 갑니다.

| STEP | 어디 | 더하는 것 | 그때 느껴야 하는 것 |
|---|---|---|---|
| 1 | 🔧 백 | 에이전트로 교체 | "화면을 한 줄도 안 고쳤는데 답이 똑똑해졌다" |
| 2 | 🖥 프론트 | 진행 과정 표시 | "**챗봇과 다르다는 게 눈에 보인다**" |
| 3 | 🔧 백 | 도구 추가 + 근거 | "도구를 더하는 건 함수 하나 더 쓰는 일이구나" |
| 4 | 🖥 프론트 | 근거 칩 | "지어낸 말인지 찾아본 말인지 구분된다" |
| 5 | 🔧 백 | 로그인 + 대화방 | "사용자가 구분되니 방도 나뉜다" |
| 6 | 🖥 프론트 | 로그인 화면 | "**서비스처럼 보이기 시작한다**" |

> 🎯 **STEP 1 → 2가 이 단계의 핵심입니다.**
> STEP 1에서 백엔드는 이미 진행 과정을 보내고 있습니다. **화면이 안 보여줄 뿐입니다.**
> STEP 2에서 화면이 그걸 그립니다. **프론트가 똑똑해진 게 아니라 백이 더 알려준 것입니다.**

---

## 8. 내 도메인으로 바꿀 자리

같은 껍데기가 모든 도메인을 받아냅니다. **바꾸는 건 세 칸뿐입니다.**

| 도메인 | 화면 입력 라벨 | 도구가 찾아올 것 (`data.py`) | 에이전트가 만들 결과 |
|---|---|---|---|
| 영업 | "고객사 정보" | 과거 제안서 · 단가표 | 제안서 초안 |
| 행정 | "민원 내용" | 부서별 업무분장표 | 담당부서 분류 + 회신문 |
| 연구 | "논문 URL" | 내 서지 목록 | 요약 + 선행연구 정리 |
| 제조 | "품번" | 재고 · 납기 테이블 | 납기 회신문 |
| 인사 | "이력서 텍스트" | 직무기술서 | 적합도 요약 |
| 마케팅 | "제품 설명" | 브랜드 톤 가이드 | 카피 3안 |
| **내 도메인** | | | |
