# 사례 연구 — 글쓰기 에이전트를 스킬 7개로 쪼개기

🟢 **전원** (읽기) · 🟡 **적용** (마지막 절)

## 이 문서가 왜 여기 있나

5단계의 [`domain_agent.py`](domain_agent.py)는 **노드 5개짜리 그래프 하나**입니다.
한 학기 동안 이걸 키우다 보면 반드시 만나는 벽이 있습니다.

> 노드 하나가 자꾸 커진다. 프롬프트가 200줄이 됐다. 고치면 다른 게 깨진다.

`marketing-sales` 리포는 이 벽을 **실제로 맞고 넘은 기록**입니다.
원래 `write` 스킬 **하나**로 글을 쓰다가, 2026-08-06에 그걸 폐기하고 **7개로 쪼갰습니다.**

이 문서는 그 7개가 각각 무엇이고, **어떤 기준으로 갈렸고, 무엇이 그걸 지탱하는지**를 정리한 것입니다.

> 📌 **"스킬"은 랭그래프 노드가 아닙니다.** Claude Code가 상황에 맞게 불러 쓰는 **지시서 파일**입니다.
> 하지만 **"하나의 큰 일을 어떤 단위로 자를 것인가"** 라는 문제는 완전히 같습니다.
> 노드로 짜든 스킬로 짜든, 자르는 기준이 이 문서의 내용입니다.

## 1. 한눈에 — 파이프라인 7개

「코드를 소재로 글을 쓴다」는 하나의 일을 **일직선 파이프라인**으로 폈습니다.

```
[0] writing-work    작업 폴더 준비        → work 폴더에 코드 사본
      ↓
[1] writing-idea    개념 키워드 3개 뽑기   → 키워드 3개 (문장 아님)
      ↓
[2] writing-draft   표 + 개조식 줄글       → draft.md (표 3행 + 줄글 15~20줄)
      ↓
[3] writing-post    말투·여백 입히기       → 발행안 + 복붙용 전문
      ↓                    └─ (뉴스레터 채널이면) writing-letter 로 갈아탐
[4] writing-pdf     첨부 PDF 4면          → _copy.md + _build.py + PDF
      ↓
[5] writing-finish  검토·이동·커밋        → post-linkedin/ 에 놓인 발행본
```

| # | 스킬 | 한 줄 | 크기 |
|---|---|---|---|
| 0 | **writing-work** | 오늘 다룰 코드를 작업 폴더로 복제 | 5.0KB |
| 1 | **writing-idea** | 그 코드에서 **명사 3개** 뽑기 | 5.7KB |
| 2 | **writing-draft** | 표로 고정하고 `~임` 종결 줄글로 | 9.8KB |
| 3 | **writing-post** | 발행 말투·서식 입히기 | 13.3KB |
| 3' | **writing-letter** | 뉴스레터 채널용 (post의 변형) | 6.2KB |
| 4 | **writing-pdf** | 첨부 PDF 만들기 | 11.9KB |
| 5 | **writing-finish** | 3인 검토 → 이동 → 커밋 | 7.4KB |

> ★ **크기가 균일하지 않은 게 정상입니다.** 판단이 많이 필요한 단계(post, pdf)가 큽니다.
> 균등하게 자르는 게 목표가 아니라 **"어디서 멈춰서 사람에게 물을 것인가"** 로 자른 것입니다.

## 2. 쪼갠 기준 — 무엇이 경계가 됐나

7개를 관통하는 경계 규칙은 **세 가지**입니다.

### 기준 ① 산출물이 바뀌면 자른다

각 스킬은 **정확히 하나의 산출물**을 냅니다. 그리고 그 산출물의 **형태**가 다릅니다.

| 스킬 | 산출물의 형태 |
|---|---|
| idea | 명사 3개 — **문장이 아님** |
| draft | 표 + `~임` 종결 줄글 — **발행 말투가 아님** |
| post | `~습니다`/`~요` 발행안 — **PDF가 아님** |

`writing-idea` 문서에 이런 줄이 있습니다.

> **설명을 길게 쓰지 않는다.** 이 단계 산출물은 키워드 3개 + 각 3~5줄이다.
> **길어지면 이미 다음 단계를 하고 있는 것이다.**

**"길어지면 다음 단계를 침범한 것"** — 이게 경계가 살아 있다는 증거입니다.

### 기준 ② 사람이 확인해야 하는 지점에서 자른다

파이프라인 문서의 「전 단계 공통」 첫 줄이 이겁니다.

> **단계마다 과정과 결과물을 출력하고 승인을 받은 뒤에 다음으로 넘어갑니다.**

즉 **스킬 경계 = 승인 게이트**입니다. `writing-post`는 한 스킬 안에서도 5번 멈춥니다
(말투 → 서식·부제 → 이해도 제고 → 복붙용 전문 → 수정 반영).

### 기준 ③ "하지 않는 것"이 곧 다음 스킬이다

**7개 파일 전부에 `## 하지 않는 것` 절이 있습니다.** 그리고 그 내용이 대개 옆 스킬입니다.

- `writing-draft` — "**발행 말투를 입히지 않는다.** 훅·CTA·시리즈 서식은 이 단계가 아니다" → 그건 `writing-post`
- `writing-post` — "**표에 없던 내용을 이 단계에서 새로 넣지 않는다**" → 그건 `writing-draft`로 되돌아갈 일
- `writing-pdf` — "**서식을 새로 설계하지 않는다**" → 직전 회차 템플릿 재사용

> 🎯 **이게 이 사례에서 가장 배울 점입니다.**
> 스킬을 쪼갤 때 「무엇을 하는가」만 쓰면 경계가 안 생깁니다.
> **「무엇을 하지 않고 누구에게 넘기는가」를 써야 경계가 생깁니다.**

## 3. 스킬 파일의 공통 뼈대

7개가 전부 같은 골격입니다. 내 스킬을 쓸 때 그대로 베낄 수 있습니다.

```markdown
---
name: writing-draft
description: (언제 이 스킬을 부르는지. 트리거 문장까지 포함)
---

# 제목 — 한 줄 요약

(앞 스킬 다음 단계다. 산출물은 ○○다. 저장 위치는 △△다.)

---

## 1. ~ N.  순서
   (번호 매긴 절차. 표와 예시 위주)

---

## 하지 않는 것
   (굵은 글씨로 금지 항목. 각각 왜인지 한 줄)

## 확인할 것
   (체크리스트)
```

### frontmatter의 `description`이 진짜 핵심

`writing-draft`의 description은 **6줄**입니다. 그 안에 이런 게 들어 있습니다.

> "초안 써라", "표로 정리하고 줄글로 써라", "용어 정확도·추상성 검토해라",
> "어휘 수정해라", "추상적인 표현 고쳐라" **같은 요청에 사용.
> 발행 말투 입히기는 이 단계가 아니다.**

- **사용자가 실제로 칠 법한 말**을 그대로 나열합니다
- **마지막에 "이건 이 스킬이 아니다"를 못박습니다**

> 💡 [`domain_agent.py`의 `classify_node`](domain_agent.py) 프롬프트와 정확히 같은 일입니다.
> "이런 요청이면 summarize" 라고 적어주는 것. **분류 정확도는 이 설명문이 만듭니다.**

## 4. 스킬별 상세

### [0] writing-work — 작업 폴더 준비

**입력** 오늘 날짜 → **산출물** `contents/work/YYYY-MM-DD-dNN/` 에 코드 사본

| 절 | 내용 |
|---|---|
| 1 | 현황 확인 (**읽기만**) — work 폴더, git log, git status |
| 2 | 오늘 Day 번호와 모듈 번호 결정. **둘은 같지 않다** (d02=모듈01, d03=모듈03) |
| 3 | 지난 Day 폴더 처리 판단. **그냥 지우지 않는다** |
| 4 | 복제할 파일을 **파일명으로** 지목 |
| 5 | **보고하고 멈춘다** ← 이 스킬의 핵심 |
| 6 | 승인 후 실행 (`git mv` + `Copy-Item` + 해시 확인) |

**5번이 존재하는 이유**가 문서에 적혀 있습니다.

> 확인 없이 폴더를 비우고 사후 보고 → **발행본이 사라질 뻔함**

보고 표에 반드시 넣는 4가지: **옮길 것 · 지울 것 · 복제할 것 · 가정**.
그리고 「가정」칸에 대한 주석이 좋습니다 — *"이게 틀리면 전부 틀린다"*.

**하지 않는 것:** 참조 폴더 수정 · **복제한 사본도 수정** · 요약본 만들기 · 모듈 짐작하기

> 사본 수정 금지에는 실제 사고 기록이 붙어 있습니다 — 2026-08-05에 사본을 고쳐서
> 원본 380줄 / 사본 457줄로 갈렸고, **산출물에 두 판의 코드가 섞였습니다.**

---

### [1] writing-idea — 개념 키워드 3개

**입력** 코드 사본 → **산출물** 키워드 3개 + 각 3~5줄

**순서 자체가 이 스킬의 전부**입니다.

```
1. 코드를 처음부터 끝까지 읽는다      (검색해서 일부만 보지 않는다)
2. 이 코드의 역할을 한 문장으로 정한다  ← ★ 키워드보다 먼저
3. 그 역할에서 키워드 3개를 뽑는다     (명사로)
4. 셋을 한 줄로 묶고, 축을 지목한다
5. 각 키워드에 코드 위치(파일+행)를 단다
```

**2번을 3번보다 먼저 하는 게 핵심**이라고 명시돼 있습니다.

> 역할을 안 정하고 키워드부터 뽑으면 `.py` 안의 **소제목을 그대로 옮기게 된다.**

키워드 3개가 갈리는 자리도 고정돼 있습니다.

| 자리 | 묻는 것 |
|---|---|
| 무엇을 만드는가 | 이 코드가 내놓는 물건 |
| 무엇으로 채웠는가 | 그 물건의 핵심 부품 |
| 왜 만드는가 | 코스 안에서 이 코드가 있는 이유 |

**맞음** `RAG` · `하이브리드 검색` · `기준선`
**틀림** "정답셋을 검색기보다 먼저 만든다" ← 문장은 키워드가 아님

**하지 않는 것:** 소제목을 개념으로 삼기 · 세부 기법(`k` 값, 가중치)을 키워드 자리에 넣기 ·
**개수 늘리기(3개 고정, 4개 나오면 하나 뺀다)** · 설명 길게 쓰기

---

### [2] writing-draft — 표 + 개조식

**입력** 키워드 3개 → **산출물** `-draft.md` 한 파일 (표 + 줄글)

#### 표는 5열 고정

| 열 | 내용 |
|---|---|
| 개념 | 키워드 (명사) |
| 에이전트와의 관계 | 에이전트 안에서 맡는 자리. **5~10자** |
| 한 줄 설명 | 그 관계가 왜 그런지 |
| 코드 원본 줄 | 행 번호 + **코드 한 줄을 원문 그대로**. 요약·재작성 금지 |
| 그 줄의 기능 | 그 한 줄이 무엇을 하는지 |

#### 줄글에 순서가 있다

> **부가 줄을 먼저 지우고, 그 다음에 연결사를 넣는다.**
> 반대로 하면 지울 줄에 연결사를 달게 되고, 지우고 나서 앞뒤 관계가 어긋난다.

연결사 표도 고정돼 있습니다 — 이유 `~기 때문임` / 결과 `그래서`·`따라서` / 예시 `예를 들어` /
추가 `마찬가지로` / 전환 `다만`·`한편` / 재진술 `즉`.
그리고 **"대략 절반 이하의 줄에만 붙인다"** — *관계가 없는 줄에 연결사를 붙이면 없는 논리를 만든 것*.

#### 저장 전 검토 5단계 — 순서가 정해져 있다

> **사실이 틀린 것을 먼저 잡고, 그 다음에 말을 고른다. 반대로 하면 지울 줄을 다듬게 된다.**

| # | 검토 | 내용 |
|---|---|---|
| 4-1 | **용어 정확도** | 코드와 대조. "요청을 받아" ← 실제로는 `state["messages"][-1]` 하나만 봄 |
| 4-2 | **병기** | 개념어에 원어. `add_conditional_edges`만 쓰고 「조건부 엣지」를 빠뜨리는 게 가장 잦음 |
| 4-3 | **추상성** | "최종 결과" → "마지막 메시지" / "조각" → "파일" |
| 4-4 | **용어 통일** | 같은 걸 두 이름으로 부르지 않기. **코드에 있는 쪽을 남긴다** |
| 4-5 | **사전 대조** | 어휘 사전의 「쓰지 않는 말」 전수 검색 |

**4-5가 왜 따로 있는지**가 명확합니다.

> 4-3은 그때그때 판정하는 단계라 **지난 회차에 이미 걸렀던 말이 매번 다시 들어온다.**

**하지 않는 것:** 발행 말투 입히기 · 분량 늘리기(표 3행 + 줄글 15~20줄) · 코드에 없는 주장 · 사본 수정

---

### [3] writing-post — 발행안

**입력** 표와 줄글 → **산출물** `## 발행안` 절 + 복붙용 전문

**한 스킬 안에서 5번 멈춥니다.**

| 세부 | 내용 |
|---|---|
| 3-1 | **말투·여백** — `~습니다` : `~요` = **6:4**. 개수를 세어 과정 표에 적음 |
| 3-2 | **고정 서식·부제** — 서식은 직전 발행본에서 복사. **부제는 개념 3개 영어 병기** |
| 3-3 | **이해도 제고** — ★ **할지 먼저 묻는다.** 자동으로 돌지 않음 |
| 3-4 | **복붙용 전문 + 점검** |
| 3-5 | **수정 반영** — 표 A / 표 B |

#### 3-2에 재밌는 규칙 하나

이모지 진행바(총 30개, 🧖 개수 = 오늘 Day 번호)를 **직전 회차에서 복사하면 안 된다**고 못박습니다.

> 2026-08-06에 Day5 블록(🧖 5개)을 그대로 복사해 **하루 멈춘 상태로 나갈 뻔했다.**

#### 3-3 이해도 제고 — "용어를 빼는 단계가 아니다"

> **용어는 정확하게 그대로 쓰고, 그 용어를 처음 만나는 사람이 읽고 넘어갈 수 있게 만드는 단계다.**
> 걸러내는 대상은 **용어가 아니라 모호한 말**이다.

| 유형 | 걸린 예 | 처리 |
|---|---|---|
| 추상 명사 | 장치 · 출구 · 자리 | 그 명사가 가리키는 **동작**을 씀 |
| 비유 | 결과가 나가는 출구 | 비유를 버리고 동작을 씀 |
| 지시 대상 없는 말 | 값 · 이걸 | 무엇인지 적음 — `점수` |
| 주어 없는 서술 | 보지 못하니까요 | 주어를 넣음 |
| 뜻이 넓은 동사 | 걸린다 · 얹는다 | 무슨 일이 일어나는지 씀 |
| **의인화** | 답하는 노드 | **코드 이름을 주어로 세움** — `generate` 노드가 답변을 만듭니다 |

그리고 판정 기준 한 줄:

> **용어를 바꿔서 문장이 짧아졌다면 잘못 고친 것이다.** 뜻풀이가 붙어 한 줄 늘어나는 것이 정상이다.

#### 3-5 수정 반영 — 표를 둘로 나눈다

| 종류 | 형태 | 처리 |
|---|---|---|
| **직접 지시** | 대화로 "이 문장을 이렇게" | **반영하고** 표 A로 보고 |
| **괄호 지시어** | 본문에 `(여기 더 짧게)` 로 적어서 돌려줌 | **바로 고치지 않고** 표 B로 제안 |

> 제안은 **문장을 완성해서** 씁니다. "짧게 줄임"이 아니라 줄인 문장 자체를.
> **2안까지만.** *3안 이상은 고르는 부담만 늘린다.*

**하지 않는 것:** 승인 전 커밋 · **글자 수 맞추려고 문장 지우기** · 표에 없던 내용 새로 넣기 ·
비유 · 엠대시 · 학력/소속 언급 · 본문에 외부 링크

> **"코드가 글의 기준이다"** — 분량이 크면 먼저 의심할 것은 **개념 배분**이지 문장이 아님.
> 한 개념이 나머지 둘을 합친 것보다 길면 거기서 무엇이 부풀었는지 짚음.

---

### [3'] writing-letter — 뉴스레터판

`writing-post` 자리에 들어가는 **채널 변형**입니다. 다른 지점만 적혀 있습니다.

| | writing-post | writing-letter |
|---|---|---|
| 고정 서식 | 직전 발행본에서 복사 | **아직 확정된 서식이 없음 — 회차마다 물어야 함** |
| 첨부 | PDF 4면 | 개념 절마다 인라인 이미지 |
| 마무리 순서 | 승인 → 발행 | **발행 → 사후 동기화**로 뒤집힐 수 있음 |

> ★ **같은 절차는 다시 적지 않고 `writing-post`를 가리킵니다.**
> (3-1 말투·여백, 3-3 이해도 제고는 "그 두 절차는 여기서 다시 적지 않고 writing-post를 그대로 따른다")
> **복사해 붙이면 두 판이 갈립니다.** 스킬을 늘릴 때 제일 중요한 습관입니다.

**하지 않는 것:** 미정인 서식을 지어 넣기 · **발행 후 동기화를 3인 검토의 대체품으로 착각하기**

---

### [4] writing-pdf — 첨부 PDF

**네 갈래로 또 나뉩니다.** `4-1 카피 → 4-2 카피 검토 → 4-3 빌드 → 4-4 렌더 검토`

> **카피를 쓰자마자 빌드하지 않는다. 렌더는 사실을 고쳐 주지 않는다.**

#### 4-2 카피 검토 — 문장 유형별로 되짚는다

가장 정교한 부분입니다. *"주장마다 근거 행을 붙이면 통과한 것처럼 보인다"* 는 문제의식에서 나왔습니다.

| 유형 | 함정 | 확인법 |
|---|---|---|
| **정의문** (`X는 …이다`) | 한 자리만 보고 정의하면 다른 자리가 반례 | 그 파일에서 `X`가 나오는 자리를 **전부** 찾음 |
| **최초성 주장** (`처음`·`비로소`) | 앞 모듈에 이미 나왔는데 처음인 척 | 파일 머리의 「쓰는 것」 목록을 먼저 읽음 |
| **주어가 옮겨간 문장** | 독자 이야기를 코드 이야기로 옮겨 씀 | 근거 행이 어느 절인지 확인 |

#### 고칠 것과 고치고 싶은 것을 가른다

> **사실 오류가 아니면 제안하지 않는다.** 어색함·중복·더 나은 표현이 보여도
> 코드와 어긋나지 않으면 **현재 문장을 유지한다.**
> 둘을 한 표에 섞으면 **사용자가 둘을 가르는 일을 대신하게 된다.**

#### 4-4 렌더 검토 — 눈으로 본다

**PNG 4장을 전부 눈으로 봅니다.** 잘림 / 겹침 / 하단 여백 / 대문자 렌더 / 표지 여백.

> 대문자 렌더 항목이 재밌습니다 — CSS에 `text-transform:uppercase`가 걸려 있어
> 섹션 헤더의 `k`가 `K`로 떠서 **코드에 없는 이름이 제목에 뜬** 사고(2026-08-06).

**하지 않는 것:** 서식 새로 설계 · 참조 폴더 수정 · 승인 전 커밋 · 본문에 없던 주장 만들기

---

### [5] writing-finish — 마무리

> **이 단계는 새로 쓰는 단계가 아니다.** 이미 확정된 두 산출물을 **검사하고 제자리에 놓는다.**

`5-1 해시 싱크 → 5-2 3인 검토 → 5-3 긴급 수정 → 5-4 사전 정리 → 5-5 이동 → 5-6 커밋`

#### 5-2 — 3인 검토관을 동시에 띄운다

| 검토관 | 보는 것 | 대는 근거 |
|---|---|---|
| **코드 정합성** | 모든 코드 인용·숫자·동작 주장 | 인용한 `.py` |
| **독자 이해도** | 발행본 + **렌더된 PNG 4장을 직접 봄** | 스타일 문서, 직전 발행본 |
| **발행 정합성** | 본문↔PDF 불일치, 고정 서식, Day 번호 | 지난 3회차 |

전부 **읽기 전용**이고, 긴급도 3단계(**발행중단 / 수정권장 / 참고**)로 답하게 합니다.

프롬프트에 넣는 것도 지정돼 있습니다.
- **이미 처리한 것은 다시 보고하지 말라고 명시** (안 하면 아는 얘기가 되돌아옴)
- 근거로 **파일 + 행 번호**를 대게 함
- 취향·스타일 지적은 빼게 함

#### 5-3 — 세 결과를 표 하나로 합친다

> **검토관별로 나눠 보고하지 않는다** — 중복이 그대로 남는다.

그리고 결정적인 한 줄:

> **검토관이 틀렸을 수 있다.** 인용한 `.py`를 열어 다시 확인하고,
> 근거가 없으면 표에 **「근거 없음」**으로 적고 **반영하지 않는다.**

#### 5-4 — 어휘 사전 정리

한 회차에서 고친 말이 **네 군데에 흩어져** 있어서 여기서 모읍니다.

| 어디서 | 무엇을 |
|---|---|
| writing-draft §4-3 | 초안에서 고친 추상어 |
| writing-post 3-3 | 말투 입히며 다시 들어와 고친 말 |
| writing-pdf 4-2 | 카피 검토에서 고친 말 |
| **사용자가 대화로 지적한 말** | ← **가장 자주 빠뜨리는 자리** |

## 5. 세분화를 지탱하는 장치 3개

스킬을 7개로 쪼개면 **일관성이 깨질 위험**이 생깁니다. 그걸 막는 장치가 셋 있습니다.

### 장치 ① 근거는 파일 하나 — "지목하지 못하면 인용하지 않는다"

같은 코드의 판이 셋(소스 `.py` / 빌드된 `.ipynb` / 작업 사본)이 되어 **셋을 섞어 인용한 사고**가 있었습니다.
그래서 규칙이 생겼습니다.

1. **인용할 파일 하나를 지목하고 산출물에 파일명으로 적는다. 지목하지 못하면 인용하지 않는다**
2. **빌드 산출물은 별개 근거가 아니다** — `.ipynb`는 `.py`에서 생성됨
3. **파생본·수정안은 인용 대상이 아니다** — 독자가 돌리면 없는 이름
4. **인용한 줄의 위치(파일 + 행 번호)를 남긴다**
5. **산문이 코드와 어긋나면 코드가 이긴다** — *원문에 있다는 것은 근거가 아니다*
6. **원본의 결함은 우회하고 기록한다** — 파생본을 만들어 해결하지 않는다

> 🎯 **5번이 특히 중요합니다.** 주석이 코드와 다르면 **코드를 믿는다.**
> 4단계에서 본 "튜토리얼은 논문 재현이 아니다"와 같은 태도입니다.

### 장치 ② 어휘 사전 — 고친 말이 자라는 파일

`contents/style/2026-08-12-lexicon.md` 하나에 **4열**로 쌓습니다.

`쓰지 않는 말` · `쓰는 말` · `원인` · `최초`(Day 번호)

세 스킬이 이 파일을 **읽고**(draft 4-5, post 3-3, pdf 4-2), 마지막 스킬이 **쓴다**(finish 5-4).

규칙 두 개가 좋습니다.

- **「원인」은 왜 추상인지를 코드에 걸어 쓴다.** "더 명확해서"가 아니라 **"대응하는 연산이 `"\n".join`이라서"**
- 왼쪽 열이 이미 있으면 **행을 늘리지 말고 「원인」만 보강한다** — *이 파일은 현재 규칙표이지 수정 이력이 아니다*

> 💡 **이게 에이전트의 "장기 메모리"입니다.** 4단계 8-1에서 본 그것이
> 벡터DB가 아니라 **사람이 읽을 수 있는 표 한 장**으로 구현돼 있습니다.

### 장치 ③ 승인 게이트 — 되돌릴 수 없는 것 앞에서 멈춘다

멈추는 자리가 전부 **되돌리기 어려운 일** 직전입니다.

| 스킬 | 멈추는 자리 | 되돌리기 |
|---|---|---|
| work | 파일 삭제·이동 **전** | 삭제는 못 되돌림 |
| post | 각 세부 단계마다 | 말투를 다 입힌 뒤엔 되짚기 어려움 |
| pdf | 확정 뒤 수정은 **표 + 승인** | 렌더는 오래 걸림 |
| finish | 커밋·푸시 | **외부 공개 문안** |

> 🎯 [4-1단계 7-2 `interrupt`](../04-agent/01-agent-basic.md#7-2-interrupt--사람-승인-hitl)에서 본
> **HITL(사람 개입)** 이 바로 이겁니다. 랭그래프에선 `interrupt_before=["act"]` 한 줄이고,
> 여기선 **"보고하고 멈춘다"** 라는 문장입니다. **구조가 같습니다.**

## 6. 실패가 규칙이 됐다

이 사례에서 가장 값진 부분입니다. 파이프라인 문서 맨 아래에 **실패 → 규칙** 표가 있습니다.

| 실패 | 그래서 생긴 규칙 |
|---|---|
| 확인 없이 폴더를 비우고 사후 보고 → 발행본이 사라질 뻔함 | 단계 0-5, **보고 후 승인** |
| 역할을 안 정하고 키워드부터 뽑아 소제목을 나열, **세 번 반려** | 단계 1-2, **역할 먼저** |
| 연결사를 먼저 넣고 나중에 줄을 지워 앞뒤가 어긋남 | 단계 2, **지우기 → 연결사 순서** |
| 부제를 추상 슬로건으로 씀 | 단계 3-2, **핵심 개념 영어 병기** |
| **12개 표현이 독자에게 안 통함** | 단계 3-3, **이해도 제고** |
| 주석을 믿고 「검색은 3건」이라 씀 — 실제론 3~6건 | 단계 4-2, **코드가 이김** |
| 「14번부터 전부 이 필드를 읽는다」가 16번에서 틀림 | 단계 4-2, **뒤 모듈을 언급하면 그 파일을 연다** |
| 섹션 헤더의 `k`가 `K`로 렌더됨 | 단계 4-4, **헤더에 코드 변수명 금지** |
| 습관대로 옵션을 걸어 하단 여백 1/4 | 단계 4-3, **분량을 먼저 재고 결정** |
| 지적이 어디를 가리키는지 확정 안 하고 **추측으로 확정본을 고침** | 단계 4·5, **확정 뒤 수정은 전/후 표 + 승인** |
| Day6만 보고 「싱크할 것 없다」고 답함 | 단계 5-1, **해시를 실제로 대조** |

> 🎯 **스킬 문서를 처음부터 설계한 게 아닙니다.**
> **한 번 틀릴 때마다 한 줄씩 늘어난 것**입니다.
>
> 여러분의 [`domain_agent.py`](domain_agent.py)도 이렇게 자라야 합니다.
> **"오늘 뭐가 안 됐는지"를 적어두는 것이 다음 회차의 규칙이 됩니다.**

## 7. 04기가 가져갈 것 🟡

### 7-1. 지금 당장 쓸 수 있는 것

[`domain_agent.py`](domain_agent.py)의 노드가 커지기 시작하면, 이 순서로 쪼개보세요.

1. **산출물의 형태가 바뀌는 곳**을 찾는다 → 거기가 경계
2. 각 조각에 **「하지 않는 것」을 먼저 쓴다** → 경계가 진짜 생기는 건 이때
3. **되돌릴 수 없는 일 직전**에 승인 게이트를 둔다
4. 조각들이 공유하는 규칙은 **파일 하나**로 뺀다 (어휘 사전처럼)
5. 틀릴 때마다 **그 조각의 「하지 않는 것」에 한 줄 추가**한다

### 7-2. 내 도메인으로 해보기

3-1의 표를 다시 꺼내서, **내 업무 하나를 파이프라인으로 펴보세요.**

| 단계 | 산출물 | 이 단계가 **하지 않는** 것 | 여기서 사람에게 물어야 하나 |
|---|---|---|---|
| 0 | | | |
| 1 | | | |
| 2 | | | |
| 3 | | | |

> **네 번째 칸이 채워지는 곳이 노드 경계입니다.**
> 하나도 안 채워진다면 그건 아직 에이전트가 아니라 **함수 하나**입니다.

### 7-3. 규모 감각

7개 스킬 합쳐 **약 59KB, 1,300줄**입니다. 하루치 글 하나 쓰자고 만든 분량이 아니라,
**30일 연속 발행**을 버티려고 만든 분량입니다.

> ⚠️ **처음부터 이렇게 쓰려고 하지 마세요.**
> `write` 스킬 **하나**로 시작해서, 안 되는 걸 만날 때마다 쪼갠 결과입니다.
> **한 학기가 있으니 여러분도 같은 순서로 가면 됩니다.**
